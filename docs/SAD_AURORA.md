# Software Architecture Document (SAD)

## Документ архитектуры программного обеспечения системы AURORA PNT

**Идентификатор:** SAD-AURORA-001
**Версия:** 0.9 (Draft на утверждение главного конструктора)
**Дата:** 2026-05-24
**Основания:** ГОСТ Р 56939-2016, ECSS-E-ST-40C, IEEE 42010-2011, arc42

---

## 1. Введение

### 1.1 Назначение документа

Документ описывает архитектуру программного обеспечения системы AURORA PNT
на двух уровнях: бортовое ПО (BSW) и наземное ПО (GSW). Документ предназначен
для разработчиков ПО, системных инженеров, тестировщиков и владельцев продукта
на стадии ОКР.

### 1.2 Контекст в проектной документации

| Документ | Связь с SAD |
|---|---|
| Технический проект §61 | Высокоуровневый обзор → детализация здесь |
| СТ (SRD), §55 | Требования FUN-* и SAT-* трассируются в компоненты SW |
| ICD-SIS-001, ICD-ISL-002, ICD-TTC-003 | Интерфейсы, реализуемые ПО |
| Кибербезопасность, §60 | Меры безопасности SW реализуются здесь |
| План V&V, §59 | Методы верификации компонентов SW |

### 1.3 Архитектурные принципы

1. **Разделение ответственности (SoC)** — каждый компонент имеет одну причину для изменения
2. **Слоистая архитектура (Layered)** — BSP → RTOS → System Services → Applications
3. **Изоляция критичности (ARINC 653 / IMA)** — partitioning для безопасности
4. **Детерминизм real-time** — предсказуемое время отклика для AOCS/NAV
5. **Криптографическая защита** — ГОСТ-алгоритмы на всех уровнях (Кузнечик, Стрибог)
6. **Локализация** — приоритет отечественных компонентов (ОСРВ «Багет», БЦВМ)

### 2.6 Системные службы (System Services)

#### 2.6.1 FDIR (Fault Detection, Isolation, Recovery)

**Уровни обнаружения:**
1. **Hardware fault** — детектируется HW watchdog (1 с)
2. **Software fault** — Software watchdog + assertions
3. **Performance fault** — мониторинг времени отклика
4. **Functional fault** — анализ данных подсистем

**Реакции:**
- L1 (мягкий): logging, повторная попытка
- L2 (изоляция): переход на резерв компонента
- L3 (Safe Mode): SunPoint, выключение ПН, отчёт в MCS
- L4 (Hard Reset): полный рестарт системы

**SLOC:** 20 000 (Ada/C)

#### 2.6.2 Clock Synchronization

**Функция:** синхронизация часов КА с UTC через ISL-цепочку или TT&C-приём.

**Алгоритм:**
1. Cs-эталон → OCXO через PLL
2. ISL TWTFT с соседними КА (каждые 10 с)
3. Калман-фильтр: оценка $\delta t, \dot\delta t$
4. Передача $a_{f0}, a_{f1}$ в NAV-app

**SLOC:** 8 000

#### 2.6.3 Memory Manager

**Функция:** управление радиационно-стойкой памятью.

- MRAM 64 ГБ: основная, EDAC SECDED Hamming + scrubbing
- Flash 1 ГБ: загрузочный код, RO + crc32
- SRAM 4 ГБ: рабочая, scrubbing каждые 100 мс

**SLOC:** 5 000

#### 2.6.4 Security HSM (Hardware Security Module)

**Функция:** хранение и применение криптографических ключей.

**Ключевые операции:**
- HMAC-SHA256 (для TESLA) — 10 мс per операция
- AES-256 (для TLM) — 1 мс per блок
- ГОСТ Кузнечик (ГОСТ Р 34.12-2015) — 2 мс per блок
- ГОСТ Стрибог (ГОСТ Р 34.11-2018) — 5 мс per блок

**Ключевая иерархия:**
- Master key (одноразовый при загрузке)
- Session keys (rotation 1 раз в орбиту)
- TESLA chain (rotation 30 с)

**SLOC:** 12 000 (включая криптоалгоритмы)

### 2.7 RTOS — Операционная система реального времени

**Основная:** ОСРВ «Багет» (НПО «Импульс») — отечественная RTOS
с сертификатом ФСТЭК уровня доверия УД-2.

**Резервная:** RTEMS (открытая, ECSS-E-ST-40C compliant).

**Конфигурация:**
- ARINC 653 partitioning: 4 partition (NAV, AOCS, ISL, TLM+SYS)
- Hard real-time scheduling: priority-based preemptive
- Memory protection: MMU enabled
- Inter-partition communication: CCSDS Subnetwork Service

### 2.8 BSP — Board Support Package

**Основная плата:** БЦВМ «Багет-83» (НПО «Электронные приборы»)
- Процессор: 1900ВМ2Т (LEON3-FT-совместимый, rad-hard)
- TID ≥ 100 крад (Si), SEL > 70 МэВ·см²/мг
- RAM: 4 ГБ ECC SDRAM
- Flash: 1 ГБ NOR
- Интерфейсы: 4× SpaceWire, 2× MIL-STD-1553B, 2× CAN, 4× UART

**Драйверы:** ~25 000 SLOC (C + некоторые ассемблерные оптимизации)

### 3.2 Сервис OD (Orbit Determination)

**Функция:** определение орбит 300 КА в реальном времени.

**Алгоритм:**
1. Получение наблюдений: pseudo-range от 21 RSN, ISL-измерения
2. Batch-least-squares фильтр с силовой моделью (J2-J6, SRP, drag)
3. Обновление эфемерид с интервалом 600 с (требование SAT-10)
4. Передача в MCS Application для генерации навигационного сообщения

**Технологический стек:**
- Python (orchestration) + Fortran (численные методы, ВНИИНИГеоПриборы)
- ~40 kSLOC
- Контейнер Docker, оркестрация Kubernetes

**Производительность:**
- Цикл OD: ≤ 300 с (от наблюдений до новых эфемерид)
- Точность: SISRE ≤ 5,2 см с SLR (требование §47)

### 3.3 Сервис Clock Estimation

**Функция:** оценка параметров часов 300 КА.

**Алгоритм:**
- Калман-фильтр: state = $[\delta t, \dot\delta t, \ddot\delta t]$ per КА
- Process noise: Allan deviation modeling
- Measurement noise: ISL + ground observations

**Технологии:** Python, ~20 kSLOC.

### 3.4 Сервис SSR Generator

**Функция:** генерация PPP-RTK State-Space Representation поправок.

**Выход:**
- Orbit corrections (radial/along/cross)
- Clock corrections
- Code biases
- Ionospheric corrections (региональные)

**Стандарт:** RTCM 3.x State-Space Representation, IGS SSR.

**Передача:** через сеть RSN → пользователи (полоса L1/L5 с задержкой ≤ 30 с
по требованию GRN-05).

**Технологии:** Python, ~30 kSLOC.

### 3.5 Сервис Plan (Planning & Scheduling)

**Функция:** планирование сеансов TT&C, CAM-манёвров, обновления ПО.

**Подкомпоненты:**
- TT&C-расписание (10 станций → 1 200 контактов/сут)
- CAM-планировщик (анализ conjunctions от 18 SDS / Роскосмос)
- ПО-апдейт планировщик
- Отчётность (выработка ресурса, заправка)

**Технологии:** Python + Celery (асинхронные задачи), ~25 kSLOC.

### 3.6 Сервис Monitoring

**Функция:** наблюдение за состоянием 300 КА + наземной инфраструктуры.

**Стек мониторинга:**
- Prometheus + Grafana (метрики)
- ELK Stack (логи)
- Alertmanager → SOC, оператор

**Алерты:**
- HW аномалии (температура, ток, напряжение)
- Точностные деградации (SISA рост)
- Кибер-инциденты (нештатные команды, аномалии трафика)

### 3.7 Сервис Security Operations (SecOps)

**Функция:** Security Operations Center (SOC) согласно §60.

**Подкомпоненты:**
- SIEM (Security Information & Event Management)
- IDS/IPS (Intrusion Detection/Prevention)
- Аудит криптографических операций
- Управление ключами TESLA + аппаратные HSM

**Технологии:** Python + Rust (критические компоненты), ~15 kSLOC.
Соответствие ФСБ КС-3, ФСТЭК УД-2.

### 3.8 API Gateway

**Функция:** единая точка входа для всех клиентов.

**Возможности:**
- REST API для пользовательских данных (SSR-поправки)
- gRPC для high-frequency обновлений
- WebSocket для real-time телеметрии
- OAuth 2.0 + ГОСТ-Кузнечик аутентификация

**Технологии:** Go или Rust, ~10 kSLOC.

### 3.9 Web UI

**Функция:** консоль оператора MCS.

**Возможности:**
- 3D-визуализация группировки (Cesium.js)
- Реал-тайм карты доступности (Leaflet)
- Графики телеметрии (D3.js)
- Аудит-логи (виртуализованный)

**Технологии:** TypeScript + React + Tailwind, ~20 kSLOC.

## 4. Деplo архитектура (Deployment)

### 4.1 Центры MCS

| Центр | Локация | Роль | Резервирование |
|---|---|---|---|
| MCS-Primary | Железногорск | Основной | 2 активных + 1 hot-spare |
| MCS-Secondary | Владивосток | Резервный | 1+1 |
| MCS-Cold | Краснодар | Холодный резерв | 1 |

**Сетевая связность:** оптоволокно с резервированием через 2 различных оператора.

### 4.2 Станции TT&C / RSN

- 10 TT&C-станций к Ф4 (2036) — см. §54
- 21 RSN-станция (мониторинг, шаг 300 км по России)
- Edge-вычисления на каждой станции (Linux + Docker)

### 4.3 Облачная / on-prem гибридность

| Сервис | Где | Причина |
|---|---|---|
| OD, Clock, SSR | On-prem MCS | Безопасность КИИ-1 |
| Web UI, API | On-prem + DMZ | ФСБ требования |
| Архив телеметрии | On-prem + бэкап в облаке | Доступ 5+ лет (GRN-06) |
| Аналитика | Гибрид | Не критично |
