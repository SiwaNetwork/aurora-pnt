## 1. Введение

### 1.1 Назначение документа

Настоящий документ определяет интерфейс служебной системы TT&C (Telemetry, Tracking, Command) низкоорбитальной навигационной системы AURORA PNT. TT&C обеспечивает:

- Передачу телеметрической информации (HK + payload) с КА на наземные станции;
- Приём управляющих команд и загрузку памяти КА;
- Двустороннее измерение дальности и точное измерение времени;
- Передачу криптографических ключей и обновлений ПО.

### 1.2 Область применения

ICD-AURORA-003 применяется к:

- Бортовой служебной радиолинии S-диапазона КА AURORA-LEO;
- Наземным станциям TT&C (НС-ТТУ, 5 объектов основного этапа → 10 к 2036 году);
- Центру управления полётом (ЦУП AURORA) и Mission Control System (MCS);
- Системе криптографической защиты информации (СКЗИ ГОСТ).

Расчёт покрытия по формуле сферической геометрии:

$$\eta_{cov} = \frac{N_{stations} \cdot \Omega_{visibility}}{4\pi}$$

где $\Omega_{visibility}$ — телесный угол видимости КА над станцией для elevation ≥ 5°.

### 3.3 Магистральная сеть

- Полоса магистрального канала: ≥ 1 Гбит/с на станцию.
- Задержка передачи в ЦУП: ≤ 100 мс (одностороннее).

## 4. Протоколы передачи

### 4.1 Стек протоколов

| Уровень | Протокол | Стандарт |
|---|---|---|
| Прикладной | XML/JSON over CFDP | CCSDS 727.0-B-5 |
| Транспортный | CFDP / Idle Mode | CCSDS 727.0-B-5 |
| Сетевой | CCSDS Space Packet Protocol | CCSDS 133.0-B-2 |
| Канальный (downlink) | AOS Space Data Link | CCSDS 732.0-B-3 |
| Канальный (uplink) | TC Space Data Link | CCSDS 232.0-B-4 |
| Физический | BPSK + кодирование | CCSDS 131.0-B-5 |

### 4.2 Space Packet Protocol

| Поле заголовка | Размер, бит | Описание |
|---|---|---|
| Version Number | 3 | 0b000 |
| Type | 1 | 0 = TM, 1 = TC |
| Secondary Header Flag | 1 | --- |
| APID (Application Process ID) | 11 | Идентификатор подсистемы |
| Sequence Flags | 2 | --- |
| Packet Sequence Count | 14 | Циклический счётчик |
| Packet Data Length | 16 | Длина payload − 1 |

### 4.3 CFDP для передачи файлов

- **Назначение:** загрузка ПО, обновление таблиц альманаха, выгрузка лог-файлов.
- **Класс операций:** Class 2 (с подтверждением, гарантированная доставка).
- **Максимальный размер файла:** 4 ГБ.
- **PDU MTU:** 1115 байт (выровнено по VCDU downlink).

## 6. Команды (uplink)

### 6.1 Типы команд

| Тип | Mnemonic | Описание |
|---|---|---|
| 0x01 | CMD_PULSE | Импульсная команда (реле, дискретный выход) |
| 0x02 | MEM_LOAD | Загрузка памяти (ПО, таблицы) |
| 0x03 | RT_CMD | Команда реального времени (немедленное исполнение) |
| 0x04 | TT_CMD | Time-Tagged команда (исполнение в заданный момент) |
| 0x05 | KEY_LOAD | Загрузка криптографических ключей |
| 0x06 | MODE_CHANGE | Переключение режима КА |
| 0x07 | MANEUVER | Команда орбитального манёвра (с подтверждением) |
| 0x08 | DUMP_REQ | Запрос на выгрузку файла/дампа |

### 6.2 Формат команды

| Поле | Размер, бит | Описание |
|---|---|---|
| Sync (ACA) | 16 | 0xACFC (CCSDS standard) |
| Spacecraft ID | 9 | 1–300 |
| Command Type | 8 | См. таблицу 6.1 |
| APID | 11 | Подсистема-получатель |
| Counter | 32 | Anti-replay, монотонный |
| Timestamp | 48 | TAI наносекунды |
| Payload Length | 16 | Размер payload в байтах |
| Payload | переменная | До 1024 байт |
| HMAC-SHA256 | 256 | Аутентификация |
| Encrypted indicator | 8 | 0=plain, 1=AES-256, 2=Кузнечик |
| CRC-32 | 32 | Контрольная сумма |

### 6.3 Аутентификация

- **HMAC-SHA256** (FIPS 180-4) или **HMAC-Стрибог-256** (ГОСТ Р 34.11-2012).
- Защита от replay-атак: монотонный 32-битный счётчик, отклонение ≥ 1 шага вперёд.
- Окно валидности timestamp: ±60 с (с учётом дрейфа борт ↔ земля).

### 6.4 Шифрование

- **Общегражданский режим:** AES-256-GCM (для совместимости с международными процедурами).
- **Военный/КИИ-режим:** **Кузнечик ГОСТ Р 34.12-2015**, режим CTR + Стрибог-HMAC.
- **Длина ключа:** 256 бит.
- **Размер блока:** 128 бит.
- **Ротация ключей:** 1 раз в неделю (KEY_LOAD).

## 7. Сеансы связи

### 7.1 Геометрия пролёта

Для орбиты h = 1000 км, наклонение 75°, минимальный угол места ε ≥ 5°:

| Параметр | Значение |
|---|---|
| Максимальная длительность пролёта | 12 мин |
| Средняя длительность | 6 мин |
| Минимальная (касательный пролёт) | **4 мин** |
| Объём данных за 4-мин пролёт @ 2 Мбит/с | **60 МБ (≈ 480 Мбит)** |

Длительность пролёта рассчитывается по формуле:

$$T_{pass} = \frac{2}{\omega_s} \arccos\left(\frac{R_E \cos\epsilon}{R_E + h}\right) - \frac{2}{\omega_E} \arccos\left(\cos\beta\right)$$

где $\omega_s, \omega_E$ — угловые скорости КА и Земли соответственно.

### 7.2 Расписание контактов

- **Планировщик:** автоматическая система AURORA Pass Scheduler (APS).
- **Период обновления плана:** 24 часа на 7 суток вперёд.
- **Приоритеты:**
  1. Аварийные контакты (CRITICAL).
  2. Загрузка ключей (KEY_LOAD).
  3. Передача навигационных обновлений.
  4. Стандартная HK.
  5. Загрузка файлов CFDP.

### 7.3 Конкуренция за станции

При одновременной видимости нескольких КА на одной НС применяется планировщик типа Earliest Deadline First (EDF) с разрешением конфликтов по приоритету.

## 8. Безопасность по ФЗ-187 (КИИ-1)

### 8.1 Категорирование

Система AURORA PNT отнесена к **объектам критической информационной инфраструктуры (КИИ) категории 1** в соответствии с ФЗ-187 от 26.07.2017.

### 8.2 Класс защиты

- **СКЗИ класс KC3** (по Положению ФСБ России ОК-Б).
- Защита от угроз: H1, H2 (внешний нарушитель с возможностями анализа протоколов).
- Криптоалгоритмы: ГОСТ Р 34.12-2015 («Кузнечик»), ГОСТ Р 34.11-2012 («Стрибог»).
- Сертификация ПО СКЗИ ФСБ России (срок действия 5 лет, перепроверка ежегодно).

### 8.3 Технические меры защиты

| Мера | Описание |
|---|---|
| Физическая защита | Контролируемая зона на каждой НС, СКУД, видеонаблюдение 24/7 |
| Защита каналов | IPSec VPN + ГОСТ-туннели между НС и ЦУП |
| Сегментация сети | Отдельные VLAN для TM, TC, MCS, OPS |
| Журналирование | Все команды, попытки доступа, изменения конфигурации (хранение 5 лет) |
| Мониторинг | СОВ (СЗИ от НСД) типа «Аргус», «КриптоПро»; интеграция с НКЦКИ |
| Резервное копирование | 3-2-1: 3 копии, 2 носителя, 1 удалённая площадка |

### 8.4 Организационные меры

- Допуск персонала по форме №3 (ФСБ).
- Регламент реагирования на инциденты — ГосСОПКА.
- Уведомление НКЦКИ в течение 3 ч при компьютерном инциденте.
- Ежегодные пентесты независимой лицензированной организацией.

## 9. Резервирование MCS

### 9.1 Архитектура Mission Control System

Структура **2N+1**:

- **Primary MCS:** ЦУП-AURORA-Калуга — активный.
- **Secondary MCS:** ЦУП-AURORA-Железногорск — активный (горячий резерв с синхронизацией данных).
- **Tertiary MCS:** ЦУП-AURORA-Севастополь — hot-spare (полностью готов к переключению).

### 9.2 Параметры отказоустойчивости

| Показатель | Требование | Достигаемое |
|---|---|---|
| Доступность сервиса MCS | **≥ 99,999 %** | 99,9994 % (расчётно) |
| Время переключения (failover) | ≤ 5 с | 2–3 с (расчётно) |
| MTBF MCS | ≥ 50 000 ч | 65 000 ч |
| MTTR | ≤ 4 ч | 2 ч (полная замена сервера) |
| Простой за год (max) | ≤ 5 мин 16 с | 3 мин (расчётно) |

### 9.3 Синхронизация данных

- **Уровень БД:** PostgreSQL Streaming Replication, синхронный режим, RPO = 0.
- **Уровень файлов:** DRBD + Pacemaker, либо CEPH-кластер.
- **Уровень сервисов:** Active-Active с балансировкой через HAProxy + Keepalived.

### 9.4 Сценарии аварийного переключения

| Сценарий | Действие | Время |
|---|---|---|
| Отказ Primary | Автопереключение на Secondary | ≤ 5 с |
| Отказ Primary+Secondary | Переключение на Tertiary | ≤ 30 с |
| Отказ всех 3 ЦУП | Деградация на автономный режим КА (ISL+AOD) | ≤ 72 ч сохранение качества SIS |
| Возврат к норме | Ручной по решению дежурного оператора | --- |

### 9.5 Доступность сервиса (расчёт)

Для системы 2N+1 с MTBF и MTTR:

$$A = 1 - \left(\frac{MTTR}{MTBF + MTTR}\right)^{N+1}$$

При N = 2 (два активных + один резерв), MTBF = 65 000 ч, MTTR = 2 ч:

$$A = 1 - (3{,}08 \cdot 10^{-5})^3 = 1 - 2{,}93 \cdot 10^{-14} \approx 0{,}9999994 \approx 99{,}99994\,\%$$

Целевой показатель доступности > **0,99999** перевыполнен.
